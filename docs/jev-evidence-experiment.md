# Jev 检查配置与独立实验

<!-- ciel-doc: current -->

顾问检查、评审证据检查和 API 配置已纳入 Ciel 0.20.0；本页先说明插件功能，再说明独立实验。

下文的独立实验脚本只研究“给定原文是否足以支持一条主张”。它是独立脚本，不加载 DSH 会话、不改写 Ciel 评审、不向真实评审增加调用。12 个样例由人工编写和标注，包含中文主张、支持、反驳、证据不足、范围扩大、搜索无命中及证据中的恶意指令。预期标签不会进入模型请求。

## 顾问建议检查

**设置 → 夏尔 Ciel → 常用设置 → 启用顾问建议检查（Jev）** 是独立开关，`advisorJevEnabled` 默认 `false`，与下方的评审证据检查互不联动。开启后，`ask_advisor` 完成回答，再由 `plugin/jev-advisor.js` 对照调用者提供的问题和背景检查建议。返回“背景支持 / 背景冲突 / 依据不足”，连同原建议交给主模型，并保存到顾问详情。背景本身未经 Jev 独立查证，建议的新颖性也不构成错误；结果只供主模型后续取舍和验证。

向配置的服务（默认 TypeSafe）发送本次问题、背景和各条建议的完整原文，使用下方共用的 Jev API 配置。每次最多一个请求、6 条建议、24 KiB 状态、64 KiB 响应，至多 10 秒且计入咨询总时限；不重试。超限、敏感输入或缺少结构化正文均明确跳过，不使用界面截短后的字段。检查失败保留顾问回答；保存关闭只中止此检查，停止咨询或关闭 Ciel 仍取消整次操作。历史建议只展示保存的结果，不补跑。

0.20.0 发布验证使用模拟 Jev 响应，覆盖真实工具输出校验、独立开关、取消、历史保存、原文保留、API 配置以及密钥持久化/脱敏/清除；完整计数和远端结果见 [发布验证记录](index.md#发布验证记录)。这不证明实际 Jev 服务的准确率。

## 评审证据检查

在 **设置 → 夏尔 Ciel → 常用设置** 中开启“启用 Jev 证据检查”并保存，`jevEnabled` 默认 `false`。密钥可在 **设置 → 夏尔 Ciel → Jev API 配置** 中填写，也可让 DSH 继承 `TYPESAFE_API_KEY`（仅官方默认接口回退）。新增环境变量仍需重启进程；通过界面保存则对下一次检查生效。代码更新后也需重新加载 Host 并刷新浏览器。文件核查需保持开启，否则没有可发送的原文引用。

`plugin/jev-review.js` 在核实完成后执行一次可选检查。开启时，存疑模型额外给出 `claim` 原文；宿主要求它是所指草稿块的精确子串（至多 1000 字符），缺少时只尝试同一疑点的批注原文锚点。不把“怀疑”改写成待证命题，也不另发模型请求提取主张。只使用最终引用的有原文回执：受限源码、最小化历史宿主事实、经检查的本轮工具输出及受限根目录清单，保留来源与观察时间；旧的空作者来源标记仍跳过。不发送完整会话、原始请求头/工具 schema、系统提示词、当前文件路径导航字段或主评审结论。敏感内容检查仍生效，但启发式筛查不能保证识别任意隐藏秘密。

每次至多 8 项、一个请求，状态总量 24 KiB，响应最多 64 KiB；原文不截短凑额度，不能检查及超出 8 项的数量明确展示。超时为剩余总时限减 1 秒和 10 秒中的较小值，不重试或跟随重定向。请求计入 `modelRequests`，实际模型及 token 用量另存于评审的可选 `jev` 字段。

评审详情显示支持／矛盾／证据不足、原始主张、引用链接、置信度、用量和分歧。分歧只是与主评审结果的标签对照（`cleared→supports`、`defect→contradicts`），供人工核对，不代表哪方正确；置信度不是正确率。`jev` 不修改 `verdict`、`coverage`、批注或回传选择。旧记录照常读取，不补跑。

缺钥、无合适输入、超时、接口错误会显示原因并保留主评审。保存关闭会中止在途 Jev，并禁止该次评审后续启动它；关闭 Ciel 或取消整次评审仍取消整个操作。API Key 仅在设置密码输入框暂存并随保存发送给 Host；原生 secret 字段对设置读取的 value/base/user 全部脱敏，界面只接收是否已配置。不进入提示词、评审记录或 Jev 错误文本。

历史接入验证（2026-09-22，非最终发布测试计数）：634 项单元测试、54 个真实 DSH 离线运行场景、22 项原生侧栏检查、原生设置开关及协议检查通过，生成客户端与 25 个打包文件检查通过。新模块另发出 1 个真实 Jev 批量请求（只含 2 条人工样例），分别得到预期的支持和矛盾；耗时 1866 ms，输入 818 / 输出 87 tokens。它验证接口接通和批量响应处理，不构成生产准确率评估。

## Jev API 设置

两个 Jev 开关共用 **设置 → 夏尔 Ciel → Jev API 配置**：

- **API Key**：密码输入框不会读取保存的原值。留空不修改，输入替换，点击“清除密钥覆盖”并保存才删除用户覆盖（若有部署层密钥则重新继承）。原生设置存储不是加密保险库，请保护本机 DSH 配置和备份。
- **接口地址**：完整 HTTPS 请求 URL，默认 `https://api.typesafe.ai/v1/systemone`，不会追加路径。禁止 URL 内凭据、查询参数、片段、明文 HTTP 和重定向。自定义服务须兼容 systemone 协议，且会收到配置的密钥与检查原文，只填写可信服务。
- **模型 ID**：默认 `jev-1.13.0`，可填写该服务支持的其他模型，不使用普通聊天模型路由。

保存后的后续检查使用新配置；在途请求保持开始时的连接参数。不填写密钥时，只有官方默认地址可使用 DSH 的 `TYPESAFE_API_KEY`，不会把环境变量密钥自动发给自定义地址。界面的“未在设置中配置”不代表环境变量不可用。新代码须先加载到 Host 并刷新浏览器；旧 Host 未声明安全字段时，API 编辑区禁用并提示重启。

## 获取和配置实验脚本密钥

在 [TypeSafe 控制台](https://console.typesafe.ai/) 获取 API Key。接口使用 Bearer 鉴权，见 [官方 API 文档](https://docs.typesafe.ai/api)。密钥只需要配置在运行实验的终端环境中，不要填到 Ciel 的 `criticModel` 字段，也不要提交到仓库。

在 Bash 终端执行，下列输入不会回显密钥，也不会把密钥明文写进命令历史：

```bash
cd /path/to/dsh-ciel
read -rsp 'TypeSafe API Key: ' TYPESAFE_API_KEY
export TYPESAFE_API_KEY
```

该环境变量只对当前终端及其子进程有效。新终端需要重新设置。脚本固定请求 `https://api.typesafe.ai/v1/systemone`，模型为 `jev-1.13.0`；不自动切换模型、重试或重定向。

## 运行

```bash
# 默认仅生成请求样例，网络请求为零
node scripts/jev-evidence-shadow.mjs --dry-run

# 配置 Key 后显式执行，最多 12 次真实请求，会产生 API 用量
node scripts/jev-evidence-shadow.mjs --live

# 可选：6 个范围边界对照样例，额外产生 6 次 API 请求
node scripts/jev-evidence-shadow.mjs --live --diagnostic

# 用完后从当前终端环境移除
unset TYPESAFE_API_KEY
```

每个请求最多等待 20 秒；首次鉴权、传输或协议错误即终止批次。结果保存在 `.artifacts/jev-shadow/` 下的独立时间戳文件中，目录被 Git 忽略。报告不写入密钥或原始服务端错误正文。脚本只发送随仓库提供的人工样例。

`dry-run` 报告中的 `completed: 0` 和 `status: not-run` 表示尚未调用模型，不能当成准确率或零误报。传输测试中的模拟回复也不代表 Jev 的实际能力。

## 如何看结果

每条真实结果记录实际模型、`supports / contradicts / insufficient`、完整概率分布、置信度、耗时和 token 用量，并与人工标签比较。后续报告也保存准确的人工样例请求，便于复现；预期标签仅用于本地比较。先人工查看 `disagreement: true` 的样例，再分析错误原因；不要从这 12 个样例确定生产阈值。`confidence` 不直接等同于正确率。

`--diagnostic` 选择另一组 6 个对照样例，专门区分“没有提供测试报告”“明确没有执行”“明确执行失败”和“只声称已执行的子集通过”。它不改写第一轮的标签或报告，用于检查分歧是否源自措辞和任务定义。

目前没有历史真实评审基线，也未把旁路结果用于正式裁决。可选模块沿用本次引用的原文和清晰的单条主张，只记录分歧；仍需独立评估误报、关键缺陷漏检和证据不足时的拒判。

## 原文读取修复

- 读取返回 `content` 原文；200 行 / 16 KiB 和整轮 128 KiB / 128 条只约束引用归档，另以 `evidence_spans` 和 `evidence_limited` 表达。
- 探索时设置 `capture_evidence:false`，搜索命中后读取上下文；找到决定性片段后，用默认 `capture_evidence:true` 的聚焦读取保存引用。
- `next_offset` 指向下一页，`null` 表示读到文件末尾。正常分页不再制造“部分覆盖”，各页保留原始换行符，可以拼回原文。字节上限实际截断请求范围时仍标记受限。
- 单文件可使用现有 8 MiB 总捕获额度，不再因超过 256 KiB 被直接排除；总容量、文件数、每次输出及敏感资料隔离边界仍然有效。
- PTC 单条日志超限明确返回错误；使用 `return` 返回原文页或分多次输出，避免静默丢失尾部。

`coverage: complete` 表示本次提名疑点均有完整的已引用证据，不表示逐字审查整个仓库。实际未核实项、缺失输入、超时及引用片段受限仍不能标记完整；无关的全局快照截断或其他未提供资料作为范围说明，不再自动否定已核实的元数据等事实。旧评审记录不被重写，新评审才应用修复。
