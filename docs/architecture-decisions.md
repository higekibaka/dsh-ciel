# 容量、部署和记录恢复决策

2026-09-19。本页把现行约束与尚未实现的能力分开。它不是承诺未来一定采用队列、数据库或自动清理。

| 项目 | 当前决定 | 什么情况下再实施 | 实施前须确定和验证 |
|---|---|---|---|
| 同会话评审 | 同一会话最多一个在途评审；重复触发明确拒绝，不排队、不重复启动模型。 | 不改变，除非产品明确需要同会话比较多个评审。 | 保持取消、超时、停用、提交点与去重回归。 |
| 服务级并发 | 没有跨会话总额度，也没有等待队列。此前八个会话的模拟并发只说明允许并行，不能作为机器容量或真实 provider 配额依据。 | 多会话负载测量显示 CPU/RSS/Worker/延迟或 provider 配额需要限制。 | 配置上限/默认值、拒绝还是排队、队列长度、公平性、超时是否含等待；取消排队与卸载清队列不得启动模型。先用当前 DSH 的真实受限 Worker 测量，再做目标部署/provider 验证。 |
| 页面缓存 | 未使用会话 LRU：最多 8 个、16 MiB 结果正文估算；在用/在途 pin。只释放内存，不删除文件。 | 真实长期使用仍超过内存目标，或单个活跃会话历史过大。 | 区分正文估算、浏览器堆/RSS和 DSH/主题资源；考虑按消息/按需查询，不能把不完整历史伪装成空记录。 |
| 单 Host、多标签页 | 支持。意向 CAS 和分诊队列在进程内跨 service 实例串行；revision 冲突由用户刷新恢复。 | 继续维持。 | 两个标签页持相同 revision 只能有一个成功，切换/重连后重新核对。 |
| 多进程共享数据目录 | **当前不支持多个 DSH Host 同时写同一 DSH_HOME/Ciel 存储目录。** 进程内队列和原子 rename 都不是跨进程事务，也没有自动防止第二个进程启动的锁。不同实例应使用各自的 DSH_HOME。 | 明确要求共享写入，或需要强制阻止误启动第二个 writer。 | 先选单 writer 租约，或支持事务的存储；验证两个真实进程 CAS、崩溃/重启、过期锁、PID 复用、路径/链接攻击和跨平台行为。不能靠无条件重试或简单最后写入获胜。 |
| 评审指纹失配 | 不自动把旧意向套到新批注上。刷新只解决客户端拿到旧指纹；如果磁盘上的意向自身绑定了旧评审，刷新后仍会冲突。 | 需要从被修改/损坏的历史恢复意向。 | 定义导出、人工核对、明确重置/重绑定及新 revision；操作前展示会失去哪些意向。无内容匹配规则时不得按相同下标迁移。 |
| 历史删除与保留 | 没有 TTL、自动清理、旧 JSONL 自动迁移或随会话归档删除 sidecar。用户意向与评审事实独立。 | 明确要求容量清理、导出、删除或迁移。 | 明确 session/review/evidence/advice/calls/feedback/inbox 的关联；删除范围、在途互斥、原子/可恢复步骤、确认文案和中断重试。关闭标签页或归档会话不代表同意永久删除。 |
| 日常部署和模型 | 本地链接只保证磁盘指向开发产物；已运行 Host/已打开 Client 仍可能缓存旧代码。 | 用户下一次正常启动/受控重载及模型验收。 | 同时核对 Host 加载与 Client 字节，验证真实路由/认证/配额/输出质量。脚本模型或 mock 通过不得代替此项。 |

这些边界不需要为本轮模块拆分增加日常配置、不需要升级依赖，也不需要删除历史。后续任务应引用具体行和验收条件；不要把这些独立需求重新包装成“尚未完成整个架构重构”。
